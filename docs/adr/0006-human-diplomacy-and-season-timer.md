# ADR-0006: การทูตมนุษย์-มนุษย์ (สงบศึก) + ตัวจับเวลาฤดู (เฟส 5 ต่อจาก ADR-0005)

**Status:** Accepted
**Date:** 2026-09-21

## Context

ADR-0005 ทำแค่ส่วนที่จำเป็นที่สุดของเฟส 5 (ห้องรอ + รหัสเชิญ + เริ่มเกมหลายคน) แล้วทิ้งรายการที่เหลือไว้ใน
ROADMAP.md: ตัวจับเวลาฤดู, การทูตระหว่างมนุษย์, ความหมายตอนจบแบบหลายคน, ยืนยัน Redis pub/sub ข้าม instance
กับห้องรอจริง, และ cold-start replay กับเกมหลายคน ADR นี้ครอบคลุมสองอย่างแรกที่ทำเสร็จในรอบนี้ (การทูต
มนุษย์-มนุษย์ กับตัวจับเวลาฤดู) และบันทึกว่าอีกสามอย่างที่เหลือ ยืนยัน/แก้ไปได้แค่ไหน (ดู ROADMAP.md เฟส 5
สำหรับสถานะล่าสุด — ไม่ซ้ำรายละเอียดไว้ที่นี่)

## Decision

**1. ข้อเสนอสงบศึกมนุษย์-มนุษย์เป็นโครงสร้างใหม่แยกจาก `PendingDecision` เดิม ไม่ใช่ต่อยอด**

`PendingDecision` ผูกกับกลไก "อำนาจต่างชาติ" (`power: PowerId`, `demand` เป็น index เข้า `DEMANDS`) และมี
ผลข้างเคียงเฉพาะทาง (บล็อกทุกคำสั่งของเจ้าของ `pending` จนกว่าจะตอบ — ดู `PENDING_DECISION` ใน
`applyAction`) การสงบศึกระหว่างมนุษย์เป็นคนละเรื่อง: ฝ่ายที่เสนอไม่ควรถูกบล็อกเทิร์นตัวเอง และไม่มี
"ข้อเรียกร้อง" ให้เลือกแบบ Lion/Eagle จึงเพิ่ม `DiplomaticProposal` (`{ id, kind: 'peace', from, to, turn }`)
กับฟิลด์ `proposals: DiplomaticProposal[]` ใหม่ใน `GameState` แยกต่างหาก และคำสั่งใหม่สองตัว
(`proposePeace`, `answerProposal`) แทนที่จะฝืนใส่ `power`/`demand` ปลอมเข้าไปใน `PendingDecision` เดิม

**2. ไม่มีค่าใช้จ่ายหรือโอกาสสุ่มเหมือน `offerPeace` เดิม (ที่ยังใช้ได้แค่กับ AI)**

`offerPeace` เดิมจำลองการติดสินบน/เจรจากับมหาอำนาจต่างชาติ (จ่ายทรัพยากร มีโอกาส 65% สำเร็จ) ซึ่งเหมาะกับ
AI แต่ไม่เหมาะกับมนุษย์ด้วยกัน — สองมนุษย์ต่อรองกันเองไม่ควรต้องพึ่งการสุ่มของเกม `proposePeace` จึงแค่ยื่น
ข้อเสนอเปล่า ๆ (ไม่มีต้นทุน) แล้ว `answerProposal` ของอีกฝ่ายตัดสินตรง ๆ ว่า `accept`/`decline` — ตรงไปตรงมา
กว่าและไม่ต้องเพิ่ม cost constant ใหม่ที่ไม่มีใครใช้จริง

**3. ข้อเสนอกรองด้วย `viewFor` เหมือน `pending` — คนที่สามมองไม่เห็น**

`viewFor()` (เดิมกรอง `pending` ให้เห็นเฉพาะของตัวเอง) เพิ่มการกรอง `proposals` ให้เหลือแค่ที่ตัวเองเป็น
`from` หรือ `to` — ป้องกันไม่ให้ผู้เล่นคนที่สามเห็นว่าใครกำลังขอสงบศึกกับใคร (เข้ากับหลักการเดิมของทั้งไฟล์:
"server ต้องไม่ส่ง state ดิบออกไป")

**4. ขอบเขตที่ตั้งใจไม่ทำรอบนี้: `tribute`/`festival`/`annex` ยังคงใช้ได้แค่กับ AI**

ทั้งสามคำสั่งใช้ `aiTarget()` เหมือนกันหมด (ผูกกับกลไกปรับความสัมพันธ์/ผนวกดินแดนที่ออกแบบมาสำหรับ AI
โดยเฉพาะ) การผนวกดินแดนของมนุษย์อีกคนโดยเฉพาะเป็นการตัดสินใจออกแบบที่ใหญ่กว่ามาก (ต้องมี flow ยอมแพ้/พ่าย
สงครามที่ชัดเจน ไม่ใช่แค่จ่ายเงินซื้อเหมือน AI) — เก็บไว้เป็นขอบเขตของรอบถัดไป ไม่ทำพร้อมกับสงบศึกในรอบนี้
เพื่อไม่ให้ ADR นี้ใหญ่เกินไปและเสี่ยงบั๊กจากการรีบทำหลายอย่างพร้อมกัน

**5. ตัวจับเวลาฤดูตรวจแบบ lazy ตอน request เข้ามา ไม่มี background job/cron แยก**

ตั้งค่า `seasonTimerSeconds` ได้ตอนสร้างห้องรอ ส่งต่อเข้า `GameRecord.seasonTimerSeconds` +
`seasonDeadline` (ISO timestamp) ตอนสร้างเกมจริง แทนที่จะรัน cron/interval แยกมาคอยเช็คทุกเกม (ซึ่งต้อง
จัดการ instance ไหนเป็นเจ้าของงานนี้ในสภาพแวดล้อมหลาย instance) `GameService` เช็คเองว่า `seasonDeadline`
เลยมาหรือยังทุกครั้งที่มี request เข้ามา (`GET /games/:id`, `POST .../actions`, WebSocket `sync`) — ถ้าเลย
แล้วและยังมีมนุษย์ไม่ ready จะยิง `endTurn` แทนให้ทุกคนที่ค้าง เข้ากับสถาปัตยกรรม polling-based ที่ห้องรอ
ใช้อยู่แล้ว (ADR-0005 ข้อ 6) ไม่ต้องเพิ่มโครงสร้างพื้นฐานใหม่

**6. endTurn ที่ตัวจับเวลาบังคับ ผ่าน `applyAction` เดียวกับคำสั่งปกติทุกประการ**

เขียนลง `game_actions` (`userId: null` เพราะไม่มีผู้เล่นคนไหนกดจริง — คอลัมน์เป็น nullable FK ไปหา
`auth.users` อยู่แล้ว) ก่อนขยับ state เหมือน `submit()` ปกติทุกประการ — สำคัญเพราะทำให้ cold-start replay
(ADR-0004) สร้างผลลัพธ์เดิมซ้ำได้เป๊ะ ไม่ต่างจากคำสั่งที่ผู้เล่นกดเอง

**7. ป้องกัน race ด้วย per-game lock เดิม ไม่ล็อกซ้ำซ้อน**

`submit()` ถือ `store.withLock(gameId)` อยู่แล้ว จึงเรียกตรวจ/บังคับ endTurn ได้ทันทีโดยไม่ล็อกซ้ำ (ล็อกซ้ำ
กับกลไกล็อกปัจจุบันจะค้าง) ส่วน `GET`/`authenticate()`/WebSocket sync ที่ไม่ได้ถือล็อกมาก่อน จะเช็คแบบ
cheap ก่อน (`isSeasonTimerDue`) แล้วค่อยขอ `store.withLock` เฉพาะตอนที่ต้องแก้จริง ๆ (ไม่ล็อกทุก request)

**8. `seasonTimerSeconds` ยังไม่ถูกเขียนลง Supabase — จำกัดขอบเขตไว้ก่อน**

ตาราง `games` ใน Supabase (migration เฟส 4) ไม่มีคอลัมน์นี้ การเพิ่ม migration ใหม่เป็นการตัดสินใจที่ควร
ทำแยกต่างหาก ไม่ใช่แถมมากับ ADR นี้ — ผลคือถ้าเกิด cold-start replay เกมนั้นจะกลับไปเป็น "ไม่จำกัดเวลา"
แทนที่จะจำค่าเดิมไว้ ยอมรับได้เพราะปลอดภัยกว่าการเดาเวลาที่เหลือผิด ๆ (ไม่ใช่ทำให้ผู้เล่นเสียสิทธิ์กะทันหัน)

## Options Considered

| ทางเลือก                                                  | ข้อดี                                                 | ข้อเสีย                                                                  |
| ------------------------------------------------------------ | --------------------------------------------------------- | ------------------------------------------------------------------------- |
| `DiplomaticProposal` แยกใหม่                                | ไม่ปนกับความหมายเดิมของ `PendingDecision`, ไม่บล็อกเทิร์นผู้เสนอ | เพิ่มฟิลด์ใหม่ใน `GameState` (schema ขยับ แต่ไม่ bump `schemaVersion`)        |
| ต่อยอด `PendingDecision` เดิม (ทำ `power` เป็น optional)      | ไม่ต้องเพิ่ม type ใหม่                                      | ผสมความหมายสองเรื่องเข้าด้วยกัน, สืบทอดพฤติกรรม "บล็อกทุกคำสั่ง" ที่ไม่ต้องการ |
| ตัวจับเวลาแบบ lazy-check ตอน request                          | ไม่ต้องมี cron/background job แยกต่อ instance                | ถ้าไม่มีใครยิง request มาเลย ฤดูจะไม่ถูกบังคับจบจนกว่าจะมีคนเข้ามา (ยอมรับได้ เพราะห้องรอก็ poll อยู่แล้ว) |
| ตัวจับเวลาแบบ background job/cron ต่อเกม                     | บังคับจบฤดูตรงเวลาแม่นกว่า แม้ไม่มีใครเข้ามาดู               | ต้องจัดการว่า instance ไหนเป็นเจ้าของงานนี้ในระบบหลาย instance ซับซ้อนขึ้นมาก |
| เขียน `seasonTimerSeconds` ลง Supabase ด้วย (migration ใหม่) | ทนต่อ cold-start replay ได้เต็มรูปแบบ                        | ต้องออกแบบ+ทดสอบ migration ใหม่ — ใหญ่เกินขอบเขตรอบนี้                       |

## Consequences

- `tribute`/`festival`/`annex` ยังใช้ได้แค่กับ AI เหมือนเดิม — การทูตมนุษย์-มนุษย์รอบนี้มีแค่สงบศึก
- `seasonTimerSeconds` ไม่ทนต่อ cold-start replay (กลับเป็น "ไม่จำกัดเวลา") จนกว่าจะมี migration ใหม่
- ตัวจับเวลาฤดูขึ้นกับมี request เข้ามาจริง (GET/action/ws sync) — เกมที่ไม่มีใครเปิดค้างไว้เลยจะไม่ถูก
  บังคับจบฤดูจนกว่าจะมีคนกลับมาเปิดดู (ยอมรับได้ในขอบเขตปัจจุบัน)
- ยังไม่ได้รัน `apps/server/test/redis-game.test.ts` กับ Redis จริงในสภาพแวดล้อมที่พัฒนา ADR นี้ (ไม่มี
  Docker) — เทสต์ห้องรอ+เกมหลายคนข้าม instance เขียนไว้แล้วแต่ยังไม่เคยรันจริง ควรรันซ้ำก่อนขึ้น production
  (`TEST_REDIS=1 docker compose up -d && npm test -w @siam/server`)
