# ADR-0005: ห้องรอ + รหัสเชิญสำหรับเริ่มเกมหลายคน (เฟส 5 บางส่วน)

**Status:** Accepted
**Date:** 2026-09-21

## Context

เฟส 1–4 รองรับผู้เล่นมนุษย์หลายคนที่ระดับ engine อยู่แล้ว (`createGame({ humans: [...] })`,
`endTurn` รอให้มนุษย์ทุกคนพร้อมก่อนคำนวณฤดู — ดู `packages/engine/src/actions.ts`) แต่ `POST /games`
สร้างได้แค่ที่นั่งมนุษย์เดียว (ผู้สร้าง) ที่เหลือเป็น AI เสมอ ยังไม่มีทางให้คนอื่นเข้าร่วมที่นั่งที่เหลือ
เฟส 5 เต็มรูปแบบมีหลายส่วน (ห้องรอ, ตัวจับเวลาฤดู, การทูตระหว่างมนุษย์, ความหมายตอนจบแบบหลายคน,
เชื่อมต่อใหม่อัตโนมัติ) — ADR นี้ครอบคลุมเฉพาะส่วนแรกที่จำเป็นที่สุด: **ห้องรอ + รหัสเชิญ** ซึ่งเป็น
เงื่อนไขเบื้องต้นก่อนจะทดสอบส่วนที่เหลือได้เลย

## Decision

**1. ห้องรอเก็บใน Store (Redis/memory) เท่านั้น ไม่ผ่าน Supabase**

ห้องรอยังไม่ใช่เกมจริง (ไม่มี `GameState`, ไม่มี seed ที่ fix แล้วจนกว่าจะ start) จึงไม่คุ้มเขียนลง
Postgres — เก็บเป็น `LobbyRecord` ใน Store ตัวเดียวกับที่เก็บ state เกม (Redis คีย์ `lobby:{code}`
TTL ค่าเริ่มต้น 1 ชั่วโมง ตามที่ ARCHITECTURE.md ร่างไว้ตั้งแต่เฟส 4, `LOBBY_TTL_SECONDS` ปรับได้) พอ
host กด "เริ่มเกม" ค่อยเรียก `GameService.createFromLobby()` ซึ่งเขียน Supabase + Redis เหมือน
`POST /games` ปกติทุกอย่าง (path เดียวกัน แค่รับที่นั่งมนุษย์หลายคนแทนคนเดียว)

**2. รหัสเชิญ 6 หลัก ตัดตัวอักษรที่อ่านสับสน**

สุ่มจากชุด `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (ตัด `0/O`, `1/I/L`) — พิมพ์/อ่านออกเสียงให้เพื่อนง่าย
กว่า UUID เต็ม โอกาสชนกัน (32^6 ≈ 10^9) ต่ำพอที่จะ retry สุ่มใหม่ไม่กี่ครั้งเมื่อชนแทนที่จะกันด้วย
transaction ที่ซับซ้อนกว่านั้น จำกัดอัตราการเข้าร่วม (`join-lobby:{ip}`) ไว้กันการเดาสุ่มโค้ดแบบ brute force

**3. host อยู่ที่นั่ง index 0 เสมอ = `p1` เสมอตอน start**

ผู้สร้างห้องเป็นสมาชิกที่นั่งแรกอัตโนมัติ คนที่เข้าร่วมถัดไปต่อคิว (`p2`, `p3`, `p4` ตามลำดับที่เข้าร่วม)
`GameService.create()` (เดิม) refactor เป็น `createWithHumans()` ส่วนตัว ที่ `create()` และ
`createFromLobby()` เรียกร่วมกัน — พฤติกรรมเดิมของ `POST /games` (สร้างที่นั่งมนุษย์เดียว) ไม่เปลี่ยน
เลยแม้แต่บรรทัดเดียว (เทสต์เดิมผ่านหมดโดยไม่ต้องแก้ไข)

**4. ล็อกต่อห้อง (`withLobbyLock`) กันสองคนกด join/leave/start ชนกัน**

ใช้กลไกเดียวกับ `withLock` ของเกม (Redis `SET NX PX` + compare-and-del / in-memory promise chain
สำหรับ memory store) แค่แยก key namespace (`lobby:{code}:lock`) เพื่อไม่แตะโค้ด `withLock` เดิมที่มี
เทสต์ concurrency ครอบอยู่แล้ว

**5. host ออกจากห้อง = ยกเลิกห้องทั้งหมด (ยังไม่มีระบบโอน host)**

ทางเลือกที่ง่ายและคาดเดาได้ที่สุดสำหรับตอนนี้ — สมาชิกคนอื่นเห็นห้องหายไป (404) ตอน poll แล้วรู้ว่าถูก
ยกเลิก ระบบโอนความเป็นเจ้าของห้องเก็บไว้ทำทีหลังถ้าจำเป็นจริง ๆ

**6. client ตรวจว่าเกมเริ่มแล้วด้วยการ poll ทุก 2 วินาที ไม่ใช้ WebSocket**

ห้องรอมีอายุสั้นและผู้เล่นไม่เกิน 4 คน โพลทุก 2 วินาทีเบากว่าการเปิดช่องทาง WebSocket ใหม่สำหรับห้องรอ
โดยเฉพาะ (ซึ่งมีอยู่แล้วสำหรับตัวเกมจริง) — `startedGameId` ถูกตั้งไว้ในห้องแทนที่จะลบห้องทันทีตอน start
เพื่อให้สมาชิกที่ยัง poll อยู่เจอค่านี้แล้วไป `GET /games/:id` ต่อได้ด้วย token ของตัวเอง (ห้องปล่อยให้
หมดอายุไปเองตาม TTL แทนที่จะลบทันที)

## Options Considered

| ทางเลือก                                   | ข้อดี                                        | ข้อเสีย                                                        |
| -------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------- |
| ห้องรอใน Store (Redis/memory)                | ไม่ต้องมี migration ใหม่, ห้องที่ไม่ได้ใช้หมดอายุเอง | ห้องหายได้ถ้า Redis รีสตาร์ตก่อน start (ยอมรับได้ อายุสั้นอยู่แล้ว) |
| ห้องรอใน Supabase (ตาราง `lobbies`)          | ถาวรกว่า, join ผ่าน realtime ได้                | ต้องเพิ่ม migration + RLS ใหม่ทั้งที่ข้อมูลอายุสั้นมาก           |
| รหัสเชิญ 6 หลัก ตัดตัวกำกวม                  | พิมพ์/บอกเพื่อนง่าย                             | โอกาสชนกัน (จัดการด้วย retry สุ่มใหม่)                          |
| รหัสเชิญเป็น UUID เต็ม                        | ชนกันแทบเป็นไปไม่ได้                            | ยาวเกินจะพิมพ์/บอกปากเปล่า                                      |
| poll ห้องรอทุก 2 วินาที                       | ง่าย ไม่ต้องเปิด WS ใหม่                        | ดีเลย์เห็นสมาชิกใหม่/การเริ่มเกมสูงสุด ~2 วินาที                 |
| WebSocket สำหรับห้องรอโดยเฉพาะ                | เรียลไทม์ทันที                                  | ต้องทำช่องทาง WS ใหม่ทั้งที่ห้องรอเป็นแค่ช่วงสั้น ๆ ก่อนเข้าเกมจริง |

## Consequences

- `POST /games` เดิมไม่เปลี่ยนพฤติกรรมเลย (ยังคงสร้างที่นั่งมนุษย์เดียว) — การสร้างเกมหลายคนต้องผ่าน
  `/lobbies` เท่านั้น
- ยังไม่มีการทดสอบ 4 คนเล่นจนจบเกมจริงข้ามเบราว์เซอร์ (เทสต์ครอบคลุมแค่ 2 คนผ่าน HTTP + engine-level
  `endTurn` รอมนุษย์ทุกคน) — ตัวจับเวลาฤดู, การทูตระหว่างมนุษย์ (สงบศึก/พันธมิตรที่ต้องตอบรับ), ความหมาย
  ตอนจบแบบหลายคน (อันดับ/ชนะร่วม), และการยืนยัน Redis pub/sub ข้าม instance กับห้องรอหลายคนจริง ยังไม่ได้
  ทำในรอบนี้ — ยกไปทำต่อ (ดู ROADMAP.md เฟส 5)
- ห้องรอไม่ทนต่อ Redis รีสตาร์ตก่อน start (ไม่มี Supabase หนุนหลังเหมือนเกมจริง) — ยอมรับได้เพราะอายุสั้น
  (นาที ไม่ใช่วัน) และ host สร้างห้องใหม่ได้ทันทีถ้าเกิดเหตุนี้
